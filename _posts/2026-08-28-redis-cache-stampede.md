새벽 2시, 알람이 울렸다. API 응답 시간이 **평소의 20배**로 튀었고, DB CPU가 100%에 붙어 있었다. 원인은 코드가 아니라 **캐시가 동시에 만료된 순간**이었다.

## 무슨 일이 있었나

인기 상품 목록을 `TTL 600초`로 캐싱하고 있었다. 문제는 이 키들이 배포 직후 **거의 동시에 채워졌다**는 것. 10분 뒤, 수천 개의 요청이 같은 순간 캐시 미스를 만나 전부 DB로 몰렸다. 이른바 **cache stampede**다.

> 캐시는 부하를 줄여주지만, "모두가 같은 시각에 만료되는" 순간을 만들면 오히려 부하를 한 점에 응축시킨다.

## 어떻게 막았나

두 가지를 적용했다. 첫째, TTL에 **랜덤 jitter**를 더해 만료 시점을 흩뿌렸다.

```python
import random

ttl = 600 + random.randint(0, 120)  # 600~720s 로 분산
redis.setex(key, ttl, value)
```

둘째, 만료가 임박하면 **확률적으로 미리 갱신**하도록 했다(probabilistic early expiration). 남은 시간이 짧을수록 갱신 확률이 올라간다.

## 배운 것

모니터링에 `cache_miss_rate`를 추가하고, 스파이크가 뜨면 알람이 오게 했다. 무엇보다 **"동시성이 만드는 패턴"**을 캐시 설계 단계에서 먼저 상상하게 됐다.

- TTL은 항상 jitter와 함께 — "동시 만료"를 원천 차단
- 캐시 미스율을 지표로 볼 것 — 눈에 보여야 대응한다
- 핫키는 조기 갱신으로 사용자가 미스를 체감하지 않게
